# ТЗ индивидуального проекта РБД

## Распределённый контур складского учёта и отгрузки по региональным площадкам

Документ приводит постановку «ритейл / склады по регионам» в **полное соответствие** требованиям файла `Задание_индивидуальный_проект_РБД.docx.pdf`.

---

## 1. Формулировка темы проекта

**Тема проекта:**  
«Горизонтально фрагментированная СУБД контура исполнения отгрузок на распределённых складских площадках».

**Тема МД:**  
«Методы организации резидентного хранения оперативных данных обеспечения объектов КИИ по региональным контурам».

**Почему это не «учебный интернет-магазин»:**  
предмет — не витрина товаров для покупателя, а **операционный контур площадок** (остатки, резерв, сборка, отгрузка, подтверждение доставки) с **запретом выноса оперативных данных за периметр региона**. Это постановка «по контуру / площадке» + «по режиму доступа», а не универсальный CRUD «пользователь / заказ / товар».

## 2. Предметная область и сущности (3НФ + FK)



### 2.1. Инфологическая модель (минимум)


| Сущность        | Назначение                                                 |
| --------------- | ---------------------------------------------------------- |
| `Region`        | Регион / периметр (ключ распределения)                     |
| `Warehouse`     | Склад на площадке региона                                  |
| `Product`       | Номенклатура (справочник; допускается реплика справочника) |
| `StockBalance`  | Остаток товара на складе                                   |
| `ShipmentOrder` | Заявка на отгрузку (жизненный цикл статусов)               |
| `ShipmentItem`  | Позиции заявки                                             |
| `ShipmentEvent` | Журнал смен статусов (фиксация контроля)                   |


Связи:

- Region **1—N** Warehouse  
- Warehouse **1—N** StockBalance  
- Product **1—N** StockBalance  
- Warehouse **1—N** ShipmentOrder  
- ShipmentOrder **1—N** ShipmentItem  
- Product **1—N** ShipmentItem  
- ShipmentOrder **1—N** ShipmentEvent

Все связи — через внешние ключи. Структура в **3НФ**.

### 2.2. Даталогическая модель (эскиз)

```text
regions(id PK, code UK, name)
warehouses(id PK, region_id FK→regions, code, name)
products(id PK, sku UK, title)
stock_balances(id PK, warehouse_id FK, product_id FK,
               qty_available, qty_reserved,
               UNIQUE(warehouse_id, product_id))
shipment_orders(id PK, warehouse_id FK, region_code NOT NULL,
                status, created_at, updated_at)
shipment_items(id PK, order_id FK, product_id FK, qty,
               UNIQUE(order_id, product_id))
shipment_events(id PK, order_id FK, from_status, to_status,
                created_at, note)
```

Ключ размещения строк оперативных таблиц: `region_code` (или `region_id`), согласованный со складом заявки.

### 2.3. Профиль запросов


| Где                                | Операции                                                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------------------------------------- |
| **Узел региона (объект/площадка)** | CRUD остатков; создание заявки; резерв; сборка; отгрузка; запись событий; локальное чтение                              |
| **Реплика региона**                | Только чтение (остатки, заявки, события)                                                                                |
| **Межрегионно / «центр»**          | Справочник `products` (реплика/рассылка); **запрещены** кросс-региональные UPDATE остатков и смена статуса чужой заявки |
| **Несколько узлов**                | Только если клиент ошибочно запросил чужой регион → **отказ по критерию**, без «тихого» фолбэка на другой шард          |

## 3. Критерий распределения (ядро соответствия заданию)



### 3.1. Правило размещения

**Критерий:** данные оперативного контура (`stock_balances`, `shipment_orders`, `shipment_items`, `shipment_events`, локальные `warehouses`) размещаются **только на узлах того региона**, которому принадлежит склад.  
Обоснование: **резидентность / периметр площадки** — при потере канала до центра региональный узел продолжает локальные операции; данные чужого региона на узел не переносятся.

Допустимая комбинация из задания:

- по контуру / площадке (регион = площадка);
- по режиму доступа (оперативные данные не покидают периметр).



### 3.2. Тип фрагментации и репликация


| Вид                                       | Что                                                                                                                                                        |
| ----------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Горизонтальная первичная фрагментация** | Разрез `shipment_`* и `stock_balances` по `region_code ∈ {ID, SG, …}` (в стенде — по одному шарду на регион)                                               |
| **Производная фрагментация**              | `shipment_items`, `shipment_events` следуют за родительской заявкой того же региона                                                                        |
| **Репликация**                            | Внутри региона: primary (писатель) → hot standby (читатель), **асинхронная** потоковая репликация (лаг фиксировать в отчёте)                               |
| **Справочник**                            | `products` — одинаковая копия на шардах (реплика справочника) **или** отдельная рассылка при старте стенда; это **реплика**, не другой фрагмент оперативки |


**Не является критерием:** «два сервера для балансировки».

### 3.3. Корректность фрагментации


| Условие             | Как обеспечивается                                                                                                                     |
| ------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| **Полнота**         | Объединение фрагментов по всем `region_code` даёт полный оперативный контур стенда                                                     |
| **Непересечение**   | Строка с `region_code=X` существует только на шарде X                                                                                  |
| **Восстановимость** | По фрагментам регионов + справочнику восстанавливается глобальная картина без потери смысла (межшардовые JOIN оперативки не требуются) |




### 3.4. Фрагмент vs реплика


| Объект                     | Классификация                                              |
| -------------------------- | ---------------------------------------------------------- |
| Шард региона ID (primary)  | **фрагмент** оперативных данных региона ID                 |
| Шард региона SG (primary)  | **фрагмент** оперативных данных региона SG                 |
| Standby ID / SG            | **реплика** своего фрагмента (только чтение)               |
| Копия `products` на шардах | **реплика справочника**, не отдельный оперативный фрагмент |




### 3.5. Отказ узла и потеря канала


| Событие                                        | Поведение                                                                                              |
| ---------------------------------------------- | ------------------------------------------------------------------------------------------------------ |
| Отказ **primary** региона                      | Запись в регион запрещена, пока нет promote; чтение — с **replica**; другие регионы работают           |
| Promote replica                                | Новый primary; запись возобновляется; в клиенте фиксируется смена роли узла                            |
| Отказ **replica**                              | Запись на primary сохраняется; чтение переключается на primary (с пометкой в клиенте)                  |
| Потеря канала «регион ↔ центр/прокси»          | Локальные операции на доступном primary региона продолжаются; чужой регион недоступен → отказ операции |
| Запрос записи/смены статуса в **чужой** регион | **Отказ по критерию контура** (даже если другой узел жив)                                              |

## 4. Техническая реализация стенда



### 4.1. Минимальный состав узлов (≥ 2 процесса СУБД)

Рекомендуемый стенд (на базе идеи geo-sharding + replication):


| Узел                         | Роль                         | Фрагмент      | Кто пишет                 | Канал           | Ожидаемый лаг      |
| ---------------------------- | ---------------------------- | ------------- | ------------------------- | --------------- | ------------------ |
| `pg-id-primary`              | писатель / объект региона ID | оперативка ID | приложение (через роутер) | Docker network  | —                  |
| `pg-id-replica`              | читатель                     | реплика ID    | никто (read-only)         | streaming async | секунды (замерить) |
| `pg-sg-primary`              | писатель / объект региона SG | оперативка SG | приложение                | Docker network  | —                  |
| `pg-sg-replica`              | читатель                     | реплика SG    | никто                     | streaming async | секунды            |
| `pgdog` (или аналог роутера) | маршрутизация по `region`    | —             | —                         | proxy           | —                  |


Допустимо упростить до **2 primary** без реплик на первом этапе, но тогда в отчёте явно описать, что чтение с реплики будет добавлено / как имитируется; для полного соответствия формулировкам задания про «чтение с реплики» лучше оставить standby.

Техника (зафиксировать в отчёте одну основную + доп.):

- **шардинг по** `region` (оправдан критерием периметра);
- **потоковая репликация** primary→replica, **асинхронная** (указать явно);
- опционально: FDW на «координаторе» только для справочной/обзорной выборки — не вместо критерия.

Имитация площадок контейнерами — **допускается**.  
«Два одинаковых тома без правила разреза» — **запрещено**.

### 4.2. Артефакты поставки

- `docker-compose.yml` + скрипты инициализации схемы на каждом шарде  
- SQL миграции / seed  
- демонстрационный клиент + зависимости  
- выгрузка/дамп или инструкция полного подъёма стенда

## 5. Демонстрационный клиент (требования задания → конкретное поведение)

Клиент (веб / консоль / desktop — на выбор) работает с **распределённой** БД, не с одной локальной таблицей.

### 5.1. CRUD по ключевым сущностям

Обязательно: `warehouses`, `products`, `stock_balances`, `shipment_orders` (+ позиции).  
Каждая операция в UI/логе показывает:

- целевой **region**;
- узел (**primary / replica**);
- результат или причину отказа.



### 5.2. Учёт распределения

- Создание заявки с `region=ID` → запись только в шард ID.  
- Выборка «заявки региона» → предпочтительно с **replica**, с пометкой источника.  
- Недоступен фрагмент региона → сообщение: «фрагмент региона X недоступен», без записи в Y.



### 5.3. Предметный сценарий сверх CRUD (обязателен)

Цепочка статусов заявки на отгрузку:

```text
CREATED → RESERVED → PICKING → SHIPPED → DELIVERED
              ↘ CANCELLED (из CREATED/RESERVED)
```

Правила:

1. **RESERVED** — увеличивает `qty_reserved`, уменьшает доступный остаток; нельзя резервировать больше `qty_available`.
2. **PICKING** — только из `RESERVED`.
3. **SHIPPED** — списание с `qty_reserved` / остатка; фиксация события.
4. **DELIVERED** — терминальный успех.
5. **CANCELLED** — снятие резерва при отмене до отгрузки.
6. Каждая смена статуса → запись в `shipment_events` (аналог «квитирования / фиксации контроля»).
7. Попытка сменить статус заявки другого региона → **отказ по критерию**.

Это закрывает требование: «хотя бы один предметный сценарий, который не сводится к INSERT/SELECT».

### 5.4. Отказы

Клиент обязан продемонстрировать:

- `docker stop` primary региона → отказ записи + чтение с replica (или явный отказ, если replica нет);  
- promote / восстановление записи;  
- отказ операции, нарушающей критерий контура.

Секреты подключений **в отчёт не включать**.
